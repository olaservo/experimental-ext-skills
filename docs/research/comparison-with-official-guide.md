# Research vs. the Official Agent Skills Client Guide

> **Scope.** Cross-checks [`clients-skills-research.md`](./clients-skills-research.md) — a fifteen-client survey of file-based skills implementations — against [`docs/client-implementation/adding-skills-support.mdx`](https://github.com/agentskills/agentskills/blob/main/docs/client-implementation/adding-skills-support.mdx) (and [`specification.mdx`](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx) where relevant). The aim is to flag (a) where the guide is descriptive of real practice, (b) patterns the guide doesn't cover but several clients implement, and (c) places where the guide and the working implementations are out of step.
>
> All client claims are sourced from the survey doc with line references; all guide claims cite line numbers in `adding-skills-support.mdx` at the agentskills repo state surveyed alongside the research.

## 2. Patterns the guide doesn't cover

These are real, working patterns the guide is silent on. Each is implemented by at least one surveyed client.

1. **Catalog token budgeting with truncation.** Codex enforces a 2 % session-token budget via `SKILL_METADATA_CONTEXT_WINDOW_PERCENT`, equally truncates descriptions before dropping any skill, and appends a warning when average truncation crosses 100 chars (research line 83). The guide's "50–100 tokens per skill" is descriptive — it does not address what to do once the catalog stops fitting.
2. **Hot-reload on filesystem changes.** Codex's `skills_watcher.rs` and Roo-Code's `vscode.createFileSystemWatcher` keep the in-memory catalog hot (research lines 85, 489). The guide treats discovery as a session-startup event.
3. **Multi-tool activation decomposition.** adk-python (`list_skills` / `load_skill` / `load_skill_resource`), mastra (`skill` / `skill_search` / `skill_read`), and agent-framework (`load_skill` / `read_skill_resource` / `run_skill_script`) all decompose activation into multiple tools (research lines 202, 562–566, 581). The guide presents a single dedicated tool.
4. **Search over the catalog.** Mastra ships a `skill_search` tool with BM25, vector, and hybrid modes for discovery beyond name/description matching (research line 565).
5. **Conditionally-registered tools.** agent-framework registers `run_skill_script` only when at least one skill has scripts; the script-runner instruction block is similarly omitted from the system prompt otherwise (research line 590). A more granular variant of the guide's "don't register a tool with no valid options."
6. **Per-load user consent.** opencode calls `ctx.ask({permission: "skill", patterns: [params.name], always: [params.name] })` on every activation (research line 326). gemini-cli's `getConfirmationDetails` shows the description and resource tree before a non-built-in skill is loaded (research line 144). The guide mentions "enforce permissions" without working through this UX.
7. **Per-agent catalog visibility.** opencode's `available()` filters via `Permission.evaluate("skill", skill.name, agent.permission)` — the only surveyed implementation that scopes catalog visibility per agent (research line 346). The guide's filtering section assumes one catalog per session.
8. **Backend-agnostic discovery.** deepagents takes a list of `sources` (filesystem, in-memory state, remote) rather than scanning the filesystem directly (research line 207). The guide's "Cloud-hosted and sandboxed agents" section treats this as a special case of provisioning skills *into* a filesystem.
9. **Versioned, content-addressable skills.** mastra splits skills into `StorageSkillType` (status `draft`/`published`/`archived`, `activeVersionId`) and `StorageSkillSnapshotType` (full content + `SkillVersionTree`) backed by a `BlobStore` (LibSQL/Postgres/MongoDB/S3/GCS/Azure). `VersionedSkillSource` reads through the tree + blob store with no filesystem; `'live'`/`'latest'`/pinned `versionId` modes layer on top of file discovery (research line 570). The guide does not address versioning.
10. **Admin-lockable enterprise skills.** cline's `RemoteConfigSchema.globalSkills` carries `{ alwaysEnabled: boolean, name, contents }`; entries marked `alwaysEnabled: true` bypass the user toggle UI and cannot be disabled (research line 468). The guide's filtering section assumes user choice is the only gating axis.
11. **Skill-body templating / preprocessing.** codex retains frontmatter on activation (research line 85). hermes-agent's preprocessor expands `${HERMES_SKILL_DIR}` / `${HERMES_SESSION_ID}` and inline `` !`shell command` `` snippets when `skills.template_vars` / `skills.inline_shell` flags are set (research line 634). The guide implicitly assumes SKILL.md is static markdown.
12. **Load-time prompt-injection scanning.** Only hermes-agent runs an `_INJECTION_PATTERNS` list against every skill body, flagging matches of phrases like `ignore previous instructions`, `system prompt:`, `<system>` (research line 640). Other harnesses treat the skills directory as a trusted root. A meaningful gap once third-party skill registries become common.
13. **Author / curator loop.** hermes-agent's `skill_manage` tool plus the background curator at `agent/curator.py` let the agent edit, archive, and create skills mid-session, indexing usage via `tools/skill_usage.py` (research line 642). The guide is consumer-only.
14. **Mode/persona scoping.** Roo-Code's `modeSlugs` array pins skills to specific Roo personas, with a three-tier priority resolution: frontmatter `modeSlugs` > frontmatter `mode` (legacy) > directory-derived `skills-{mode}/` (research lines 482–487). The guide doesn't cover scope axes beyond project / user.
15. **Registry-not-prompt-builder architecture.** VS Code surfaces skills as `ChatSkill` items via `ChatSessionCustomizationProvider`; there is no model-facing catalog string built by the host. The editor hands the SKILL.md `Uri` to an embedded session (Copilot CLI / Claude Code) and delegates skill semantics to it (research lines 412–430). The guide implicitly assumes the host renders a catalog into a prompt.
16. **Path compaction for token savings.** openclaw's `compactHomePath` rewrites absolute paths to start with `~/` before injection, saving ~5–6 tokens per skill (research line 352). A small but worth-mentioning catalog-rendering optimization.
17. **Catalog-stable sorting for cache hits.** mastra sorts by name when rendering the catalog so repeated activations across turns hit the prompt cache (research line 537). Not addressed in the guide.

## 3. Where the guide and the working implementations are out of step

1. **`description` missing or empty → skip.** The guide is unambiguous (line 134). goose's frontmatter struct defaults `description` to `""` and loads the skill anyway (research lines 388–394), so the model sees `• name -` with an empty tail. cline's parser is similarly fail-open, returning `{data: {}, body: markdown}` for malformed frontmatter (research line 449). The guide's rule is stricter than the laxest implementations, though a majority of clients do skip.
2. **`allowed-tools` is "experimental" — but ornamental everywhere.** The spec marks it experimental (`specification.mdx` line 167). The research found it parsed in adk-python, fast-agent, deepagents, crewAI, hermes-agent, openclaw, mastra, and agent-framework — and *enforced almost nowhere*. crewAI explicitly never references the field outside `models.py` (research line 530). Roo-Code explicitly notes no enforcement (research line 503). hermes-agent stores it as metadata only (research line 640). The "experimental" caveat in the spec is generous: in practice the field is metadata, not a tool allowlist.
3. **Frontmatter extension is fragmented.** Codex's `SkillPolicy.allow_implicit_invocation` and `SkillPolicy.products`, Roo-Code's `modeSlugs`, mastra's versioning fields and richer `metadata`/`license`/`compatibility` use, hermes-agent's `platforms` / `required_environment_variables` / `setup.collect_secrets` / `requires_tools` / `fallback_for_tools` are all spec-extending fields in production today (research observation 7, lines 596–615). The guide treats the spec as a stable reference; it does not address the portability story for vendor-specific fields, which the metadata field alone doesn't fully solve.
4. **System-prompt vs. tool-description placement: presented as alternatives, but the strongest implementation does both.** The guide says "Both work" (lines 188–194). gemini-cli embeds the catalog in the system prompt, in the `activate_skill` tool description, *and* enum-constrains it in the schema — three places (research lines 105–125). Worth flagging as a belt-and-suspenders option, not just an XOR choice.
5. **Eager injection (crewAI) breaks the progressive-disclosure premise.** Of the fifteen surveyed clients, crewAI's standard `Crew(agents, skills=...)` flow eagerly inlines every activated skill body into the task prompt at agent-init time via `append_skill_context`, with no model-driven activation tool (research line 522, observation 8). The guide presents progressive disclosure as universal; in practice, at least one well-known client ships "skills support" while skipping it.

## 4. Suggested edits to the guide if folding any of this in

In rough priority order (most-impactful first):

1. **Add a token-budgeting subsection in Step 3.** Use codex's 2 %-budget-with-equal-truncation as the worked example. Mention openclaw's `~/...` path compaction as a smaller optimization. Mention mastra's stable-sort for prompt-cache stability.
2. **Add a trust subsection in Step 4 beyond "project trust gate."** Cover (a) per-load user consent (opencode), (b) load-time content scanning (hermes-agent's `_INJECTION_PATTERNS`), and (c) admin-lockable remote skills (cline's `alwaysEnabled`).
3. **Acknowledge multi-tool activation in Step 4.** The single `activate_skill` framing implicitly recommends a one-tool design; adk-python / mastra / agent-framework decompose into 2–3 tools and the guide should mention this is a valid alternative, not an aberration.
4. **Add hot-reload to Step 5** alongside compaction-protection and dedup. Two surveyed clients implement it; it is a real "manage skill state over time" concern.
5. **Add a brief acknowledgment of registry-not-prompt-builder hosts.** A short note that VS Code's `ChatSessionCustomizationProvider` model is a legitimate alternative architecture — the host hands SKILL.md `Uri`s to an embedded agent rather than rendering a catalog string itself. Useful for skills-over-MCP discussions.
6. **Mention preprocessing as a real variant of "What the model receives."** codex retains frontmatter; hermes-agent expands template variables and inline shell. The guide's "full file vs. body only" framing doesn't quite fit a preprocessing pass.
7. **Acknowledge eager injection as an anti-pattern.** A short call-out in the progressive-disclosure intro that crewAI exists and skips disclosure entirely, so the reader doesn't think the three-tier model is universally enforced.
8. **Either retire or qualify the "skip on missing description" rule.** Either soften to "warn-and-load with placeholder" to match goose / cline, or strengthen the spec language so non-skipping behavior is explicitly out-of-spec.
9. **Add a portability-of-extensions note to Step 2.** The spec's `metadata` field is the official extension surface, but four clients are using top-level frontmatter keys instead. The guide could recommend `metadata.<vendor>.<field>` as the portable pattern.

## Notes on what was *not* validated

- The research doc pinned permalinks at survey time; this comparison did not re-fetch them, so any client behavior that has changed since those commits is not reflected here.
- Closed-source harnesses (Claude Code, Cursor, Sourcegraph Amp) were out of scope for the research and remain so here.
- The guide may have been updated upstream since the local copy under `related-work-repos/agentskills/` was synced. Re-check before filing PRs.
